# CareShift Guard デプロイ手順

Oracle Cloud Infrastructure（OCI）上に構築する手順。
**検証環境（Always Free）** と **本番提案環境（有料）** を分けて記載する。

最終レポートのデモには検証環境を使う。
本番提案環境は費用の根拠を示すための構成であり、実際に構築する必要はない。

---

## 0. 事前準備

| 項目 | 内容 |
|---|---|
| OCIアカウント | Oracle Academy Cloud Program または個人のFree Tier |
| SSH鍵 | `ssh-keygen -t ed25519 -C "careshift"` で作成 |
| GitHubリポジトリ | 公開リポジトリとして作成済みであること |
| 所要時間 | 初回で約60〜90分 |

### Always Free 枠の現状（重要）

**2026年6月15日、Always Free の Ampere A1 割当が 4 OCPU・24GB から
2 OCPU・12GB へ半減されました。** 公式のアナウンスはなく、
ドキュメントの更新のみでした。

したがって検証環境は **2 OCPU / 12GB の1インスタンス** に収める。
この制約は本ソリューションの構成（3コンテナ）で問題なく満たせる。

またOracleのドキュメントには「既存リソースを一度終了した場合、
更新後の上限を超えるリソースを再作成できない可能性がある」と
記載されている。**インスタンスを不要に削除しないこと。**

## 1. インスタンスの作成

OCIコンソール → Compute → Instances → Create instance

| 設定項目 | 値 |
|---|---|
| Name | `careshift-demo` |
| Placement | 大阪リージョンの任意のAD |
| Image | Canonical Ubuntu 26.04（無い場合は 24.04。※後述） |
| Shape | Ampere → `VM.Standard.A1.Flex` |
| OCPU / Memory | **2 OCPU / 12 GB**（Always Free の上限） |
| Boot volume | 100 GB |
| VNIC | パブリックIPを割り当てる |
| SSH keys | 作成した公開鍵を貼る |

> **Ubuntu 26.04 のイメージが一覧に無い場合**
> 24.04 LTS を選ぶ。アプリとデータベースはすべてコンテナ内で動作するため、
> ホストOSの版はアプリの動作に一切影響しない。
> これはコンテナ技術を採用したことによる利点である。

### ネットワークの開放

VCN → Security Lists → Default Security List → Add Ingress Rules

| Source CIDR | Protocol | Destination Port |
|---|---|---|
| `0.0.0.0/0` | TCP | 80 |
| `0.0.0.0/0` | TCP | 443 |

**注意。** OCI はセキュリティリストとは別に、
インスタンスのOSファイアウォール（iptables）も既定で閉じている。
両方を開けないと外部から到達できない。ここでつまずく人が多い。

```bash
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
sudo netfilter-persistent save
```

## 2. ホストの準備

```bash
ssh ubuntu@<パブリックIP>

sudo apt-get update
sudo apt-get install -y ca-certificates curl git make

# Docker 公式リポジトリを追加（Ubuntu 同梱版は古い）
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) \
signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker ubuntu
newgrp docker

docker --version
docker compose version
uname -m          # aarch64 と表示されること
```

**`aarch64` であることを必ず確認する。** Ampere A1 は Arm である。
x86_64 向けのイメージは動かない。本ソリューションが使う
Python 3.13 / PostgreSQL 18 / nginx の公式イメージはいずれも
arm64 に対応しているため、そのまま動く。

## 3. アプリケーションの配置

```bash
git clone https://github.com/FloatedGecko667/careshift-guard.git
cd careshift-guard

make init                    # .env を作成
```

`.env` を編集して秘密情報を設定する。**既定値のままでは本番起動できない**
（`app/config.py` が起動時に検出して失敗させる）。

```bash
# 強い値を生成する
openssl rand -base64 32      # POSTGRES_PASSWORD 用
openssl rand -hex 32         # SECRET_KEY 用

nano .env
```

```ini
POSTGRES_PASSWORD=<生成した値>
SECRET_KEY=<生成した値>
APP_ENV=production
SOLVER_TIME_LIMIT=10
SOLVER_WORKERS=2             # 割当OCPU数に合わせる
PUBLIC_HOSTNAME=<ドメインまたはIP>
```

```bash
make vendor                  # htmx を取得（任意）
make up                      # ビルドと起動
```

初回のビルドは OR-Tools の取得に時間がかかる。
2 OCPU の環境で **5〜10分** 程度を見込む。

```bash
docker compose ps            # 3コンテナが healthy になること
make logs                    # 異常がないか確認
```

## 4. データベースの初期化

```bash
make migrate                 # db/schema.sql を Alembic 経由で適用
make seed                    # 人員配置基準ルールと初期データを投入
```

適用結果を確認する。

```bash
make shell
```

```sql
\dt                                    -- 10テーブルが並ぶこと
\dv                                    -- v_daily_fte があること
SELECT job_type, formula_type, base_fte, threshold_users, step_users
FROM staffing_rules WHERE service_type = 'day_service';
SELECT code, name, start_minute, end_minute, break_minutes, work_minutes
FROM shift_patterns ORDER BY display_order;
\q
```

`work_minutes` が生成列として自動算出されていることを確認する
（早番 420→960 休憩60 なら 480分）。

### 管理者パスワードの設定

`seed.sql` の `password_hash` はプレースホルダである。
実際に使える値へ置き換える。

```bash
docker compose exec web python3 -c "
from app.security import hash_password
print(hash_password('ここに設定したいパスワード'))"
```

出力されたハッシュ値で更新する。

```bash
make shell
```

```sql
UPDATE users SET password_hash = '$argon2id$...'
WHERE email = 'admin@example.jp';
\q
```

## 5. 動作確認

### サーバ内部から

```bash
curl -s http://localhost:8080/healthz
# {"status":"ok","database":"up"}
```

`database` が `up` であることを確認する。`down` の場合は
`.env` の接続情報か db コンテナの状態を疑う。

### 外部から

ブラウザで `http://<パブリックIP>:8080/` を開く。

到達しない場合の切り分け順序は次のとおり。

1. `docker compose ps` で nginx が起動しているか
2. サーバ内から `curl localhost:8080` が通るか（通ればアプリは正常）
3. OCI のセキュリティリストで該当ポートを開けたか
4. `sudo iptables -L INPUT -n --line-numbers` でOS側が開いているか

**2が通って3か4で止まっているケースが最も多い。**

### スモークテスト

```bash
docker compose exec web python3 -m scripts.smoke_test
```

11項目すべてが OK になることを確認する。

## 6. TLS の設定（任意・デモでは省略可）

独自ドメインを持っている場合のみ。

```bash
sudo apt-get install -y certbot
sudo certbot certonly --standalone -d <ドメイン> \
  --agree-tos -m <メールアドレス> --non-interactive
```

`nginx/default.conf` に 443 の server ブロックを追加し、
証書のパスをマウントする。

本番提案環境では OCI Flexible Load Balancer で TLS を終端するため、
この作業は不要になる。

### アドレスバーを含める理由

「ローカルで動かしただけではないか」という疑いを先に潰すためである。

## 8. デモ後の停止について

**インスタンスを削除しないこと。** Always Free の上限が縮小された経緯があり、
一度終了すると同じ構成で再作成できない可能性がある。

費用をかけずに止めたい場合はインスタンスを Stop する。
Always Free の枠内であれば、起動していても課金されない。

## 付録A. 本番提案環境の構成（費用根拠）

顧客に提供する構成。Pay As You Go 契約を前提とする。

| 項目 | 構成 | 月額（税別・165円/USD） |
|---|---|---|
| VM1（nginx + web） | Ampere A1 2 OCPU / 12GB | 4,577円 |
| VM2（PostgreSQL 18） | Ampere A1 2 OCPU / 16GB | 5,300円 |
| ブロックボリューム | 100GB Balanced | 701円 |
| オブジェクトストレージ | 100GB | 421円 |
| ロードバランサ | 10Mbps | 0円（有料アカウントは1台目・10Mbpsまで無償） |
| 送信データ転送 | — | 0円（全リージョンで無償） |
| 監視 | OCI Monitoring / Alarms | 0円（標準機能） |
| **合計** | **50テナント収容** | **10,999円** |

1テナントあたり **220円/月**。月額利用料 16,500円に対する
インフラ原価の比率は 1.3 パーセントである。

### 本番環境で無料枠を使わない理由

無料枠には SLA がなく、予告なく縮小され得る。
実際に2026年6月、Ampere A1 の割当が半減された。

「補助金を前提としない」という条件と同じ論理で、
**無料枠を前提とした収益計画も成立しない**と判断した。
検証環境は無料枠、顧客に提供する本番環境は有料契約と明確に分離する。

## 付録B. つまずきやすい点

| 症状 | 原因 | 対処 |
|---|---|---|
| 外部からアクセスできない | OSファイアウォール | 手順1の iptables を実行 |
| ビルドが極端に遅い | 2 OCPU で OR-Tools を取得 | 待つ。5〜10分は正常 |
| `database: down` | 接続情報の不一致 | `.env` と compose の環境変数を確認 |
| 起動直後に web が落ちる | SECRET_KEY が既定値のまま | `.env` を修正。設計上の意図的な失敗 |
| exec format error | x86_64 向けイメージ | `uname -m` で aarch64 を確認。公式イメージを使う |
| メモリ不足でビルドが失敗 | 12GB を超過 | `docker builder prune` の後に再試行 |
| シフト生成が10秒で終わらない | 職員数が多い | `SOLVER_TIME_LIMIT` を延ばす。上限到達でも最良解が返る |
